# Native compatibility

The native support table is generated from repository evidence. The web and native sides share blueprint validation and semantic conformance for the fixtures covered by the native test suites; this does not mean every catalog component paints on every target.

## Current platform boundaries

- **Web:** the TypeScript renderer is the complete catalog renderer.
- **Compose Desktop:** the JVM renderer paints a subset of catalog components. Other valid nodes use visible placeholders; some painted data views are read-only.
- **Kotlin Multiplatform spec:** the shared contract compiles for JVM and iOS arm64 targets. The iOS target is for the spec module, not a Compose UI renderer.
- **Android renderer and Compose iOS renderer:** planned; there are no configured UI targets for them today.

Native modules are in development and are not published to Maven Central. Do not treat a configured Kotlin target as evidence that a native UI renderer exists there.

## How status is derived

`native/docs/parity.json` is generated by `scripts/native-parity.ts` from the spec catalog and Compose registry. `src/data/native/compatibility.ts` combines that catalog with configured Gradle targets, native renderer source files, and checked-in conformance traces. Component and platform statuses are derived from those inputs; they are not hand-entered table rows.

The compatibility page shows the generated component status, platform group, and evidence paths. The source files for individual behavior and trace coverage are listed in `native/docs/PARITY.md`. Recheck the generated catalog after source changes with:

```bash
pnpm exec tsx scripts/native-parity.ts --check
```

## Reading the status

A painted component can still have a narrower native prop set or read-only behavior. A shared validation or semantic trace demonstrates only the contract covered by that fixture; it is not a pixel-equivalence claim. A placeholder is explicit unsupported rendering, not a claim that the component is available natively.
