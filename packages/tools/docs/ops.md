# Operations registry

**Package:** `@texuli/tools` · **Import:** `@texuli/tools/ops` · **Path:**
`src/ops/` · **Decision:** [ADR-017](../../../docs/DECISIONS.md#adr-017-one-operations-registry-texulitoolsops-for-every-agent-surface)

> **Status: released in `0.9.0`.** The `./ops` subpath ships in
> `@texuli/tools` from `0.9.0` (pre-1.0; under 0.x a new minor may break).
> The tables under [Operations](#operations) are
> generated from the registry by `scripts/generate-surfaces.ts`, and
> `pnpm check:surfaces` fails when they drift; edit the operations, not the
> tables.

Every capability an agent can call is one **operation**, declared once. Each
has a `group.verb` name, a title, a summary written for agents, a JSON Schema
input and output, annotations, a runtime class, limits and worked examples.
The MCP server (`src/mcp/`, local and remote) lists and calls them, the
`texuli <group> <verb>` router runs each one, and the `texuli deck`,
`texuli document`, `texuli ds` and `texuli theme list|preview` commands run
through the same registry. The design-system operations are described in
[ds.md](ds.md). The registry is framework-free.

The `deck.run` commands are in [deck.md](deck.md) and the `document.run`
commands in [document.md](document.md). Input bytes are the UTF-8 size of
the input as JSON. The time budget is checked whenever the handler yields
(it awaits a promise); a synchronous handler cannot be interrupted, so the
deck commands are bounded by their input size instead. `blueprint.validate`
accepts the catalog's 256 KiB tree cap plus 8 KiB, and its item cap is the
catalog's 512-node tree cap.

**Runtime classes.** `edge` operations are pure compute and run anywhere.
`node` operations need Node (here, the PDF and DOCX writers, which are kept
off the edge on purpose). `site` operations read the built texuli.com and
only the remote MCP serves them (see [Site operations](#site-operations)).
A door passes the classes it serves (`LOCAL_RUNTIMES`, `['edge', 'node']`,
for stdio and the CLI; `REMOTE_RUNTIMES`, `['edge', 'site']`, for
`https://texuli.com/mcp`) and `invoke()` refuses the rest with
`runtime-unavailable`. The catalog operations read the static manifest list
of `@texuli/catalog/manifests/all`, so they need no file system.

**Annotations.** Every operation today is `readOnly: true`,
`destructive: false`, `idempotent: true` and `openWorld: false`; the MCP
server publishes them as `readOnlyHint`, `destructiveHint`, `idempotentHint`
and `openWorldHint`.

## Site operations

`site.pages`, `site.read` and `site.search` (PLAN_011 T-ar-site-mcp,
[ADR-018](../../../docs/DECISIONS.md#adr-018-the-remote-mcp-on-pages-functions))
read the built site, so they are the `site` runtime class and only the
remote door serves them. They never fetch the network: a door passes
`invoke(name, input, { runtimes, site: { assets, origin } })`, where
`assets` has the shape of Cloudflare's `env.ASSETS` binding
(`fetch(request) → Response`), and the remote Function passes its own
binding and the request origin. Without `site`, they answer
`runtime-unavailable`.

- **The index** is the website build's `md-manifest.json`: besides the
  `twins` map, its `pages` list gives each page's path, twin path, title,
  description and h2/h3 headings (at most 64, read from the twin outside
  code fences). It is parsed once per binding, capped at 4 MiB, and only
  entries with a plain route and a plain `.md` twin path under the site root
  are kept.
- **`site.pages`** lists the pages in path order, optionally under a path
  `prefix`, with `offset` and `limit` (at most 200) and `nextOffset` while
  more follow.
- **`site.read`** returns one page's Markdown twin. The path may be a route
  (`/guides/theming/`), the same without the slash, the twin
  (`/guides/theming.md`, `/index.md`), `…/index.html`, or a texuli.com URL
  (the request origin's host is accepted too). Traversal (`.` or `..`
  segments), percent-encoded or backslashed paths, `//`, other hosts and
  schemes and characters no page uses are refused as `invalid-input`; a
  well-formed path that is not in the manifest is `not-found`. The caller's
  path only selects a manifest entry: the asset request is always the twin
  path the manifest names. A twin over 256 KiB is cut at a character and
  line boundary and returned with `truncated: true`.
- **`site.search`** ranks pages by the query's words (lowercase letters and
  digits, at most 12): pages that match more words first, then the score
  (title word 10, in the title 6, path word 4, in the path 2, heading word
  3, in a heading 2, in the description 2, plus 8 when the whole phrase is
  in the title and 4 when it is in a heading), then the shorter path, then
  the path. The same query always gives the same answer. Each hit names up
  to three matching headings.

**Local doors do not list them.** The stdio server and the CLI serve `edge`
and `node` only: they have no built site to read, and an agent working
locally reads the repository's own pages and docs. A `--site <dir>` reader
over a local `dist` was considered and left out: it would add a file-system
reader to the local door for content the remote door and the repository
already provide. Calling a site operation locally answers
`runtime-unavailable` (an MCP `isError` result; the CLI has no `site`
group).

## Blueprint validation

`blueprint.validate` wraps `validateDraft` from `@texuli/catalog/validate`
(see the catalog's `docs/validate.md`) so any door can check a blueprint:

- **Input:** `draft` (a catalog tree `{ id, props, children }`, an array of
  trees, or a `texuli-blueprint` envelope), `tier` (`untrusted`, the
  default, or `developer`) and `fragment` (`true` accepts any roots; by
  default the single root must be `layout-page`, `layout-doc`,
  `layout-deck`, `document`, `canvas` or `data-dashboard`).
- **What runs:** the catalog's checks in order (input, envelope, structure,
  interaction, sinks, limits, render, blocks, documents, forms, canvases,
  sheets, grammar, root), against the catalog `catalog.search` reports
  (an envelope written for another catalog hash fails with
  `catalog-mismatch`), with the deep block family schemas and
  `validateDocument` from `@texuli/document/schema` for `document` nodes.
  The tier the draft declares is ignored, as in every host. An envelope's
  `designSystem` (spec `0.10.0`) goes through the spec's
  `checkDesignSystemReference` as the catalog's `checkDesignSystem` hook,
  so an inline document's codes (`unknown-key`, `url-refused` …) land
  under `$.designSystem` at the caller's tier (from `0.10.0`). `blueprint.theme` sets that field and also compiles an inline
  document for the guarantee codes ([ds.md](ds.md)).
- **Output:** `valid` (true only with no error diagnostics), `status`
  (`valid`, `invalid`, `parse` or `over-limits`), `tier`, `migratedFrom`
  (the spec version an envelope declared, when it was migrated; an envelope
  without `spec` is `0.2.0`) and `diagnostics`, each with `check`, `code`,
  `severity`, `path`, `message` and, for a node, its `id`. The codes are the
  catalog's own (`sink`, `tier-denied`, `nodes-exceeded`, `frame-root`,
  `catalog-mismatch` …); the catalog has no `hint` field, so none is added.
  A `block-schema` diagnostic also names the shape expected at the failing
  path and points at `block.schema`, e.g. `block columns.0: Expected a plain
  object. Expected shape: { id: string, label: string }. Read block.schema
  with type "table" for the full shape and examples.` The text is generated
  from the block shapes below, never written per type. The shapes load as a
  lazy chunk that `blueprint.validate` and the `block.*` operations load
  first; the email and print outputs validate synchronously and add the
  shape only when the chunk has already loaded in that process.
- **Not checked on this server:** `schema-form`, `canvas` and `spreadsheet`
  nodes and `{"$source": …}` bindings are refused (`form-unchecked`,
  `canvas-unchecked`, `sheet-unchecked`, and source bindings), because `@texuli/tools`
  does not depend on `@texuli/forms`, `@texuli/canvas` or `@texuli/sheets`
  and holds no data sources. The full spec check of an envelope
  (`validateBlueprint` from `@texuli/spec`) is skipped for the same reason;
  the catalog-local interaction check always runs. When `when` conditions
  appear, they are refused (`invalid-condition`): no condition runtime is
  passed.

## Block shapes

The `blocks-*` components take a `block` prop whose shape depends on its
`type`. `block.list` lists every type the validator accepts (the catalog's
`BLOCK_FAMILY_TYPES`, by component), and `block.schema` returns one type's
shape. The block families validate with hand-written parsers, not schema
objects, so the shape is learned from the validator
(`src/ops/block-shapes.ts`):

- **Types:** exactly the validator's list; a test fails when a validated
  type is not served.
- **Examples:** `BLOCK_CATALOG` from `@texuli/blocks/core`, plus fixtures in
  `block-shapes.ts` for the eleven types it has no entry for yet (diagram,
  embed, interactive and map families). Only examples that pass the family
  check and the untrusted sink scan are served, so every served example
  validates in a blueprint.
- **Shape:** the examples' merged structure as compact text (`shape`) and
  as a derived JSON Schema (`schema`). A field is required only when the
  family parser refuses the example without it. An object keyed by ids
  declared elsewhere in the block (a table row keyed by column ids) is a
  record, and a nested block is `Block`. Fields no example shows are not
  listed, enums show as `string`, and `limits` carries the caps in words:
  the validator stays authoritative.
- **Usable in a blueprint:** `usableInBlueprint` is false, and `notes` says
  why, when no instance passes `blueprint.validate` at the untrusted tier.
  Today that is `tree`: its parser requires `style`, and the draft sink scan
  refuses every `style` key. The rich `list` example (`style: "check"`) is
  not served for the same reason.

## Library

```ts
import { REMOTE_RUNTIMES, TEXULI_OPERATIONS, texuliOps } from '@texuli/tools/ops';

texuliOps.list({ runtimes: REMOTE_RUNTIMES }); // what the remote door serves: edge and site
const outcome = await texuliOps.invoke('catalog.search', { query: 'card', tier: 'untrusted', limit: 5 });
if (outcome.ok) outcome.output; // { hash, fileName, total, entries, limit }
else outcome.error; // { code, message, issues? }
```

`invoke(name, input, { runtimes, site })` never throws. It checks the input is a
plain JSON object within `limits.inputBytes`, validates it against the
input schema, runs the handler under the time budget, and validates the
output against the output schema. `createOperationRegistry(operations,
aliases)` builds another registry (an adopter's own operations, or a test
double); it refuses duplicate names and schemas outside the supported
subset. `defineOperation` types a declaration; `TOOLS_VERSION` is the
package version, read from `package.json` (the MCP `serverInfo.version`).

### Error codes

| Code | When |
| --- | --- |
| `unknown-operation` | The name is neither an operation nor an alias; a name removed in `0.10.0` gets a message naming its replacement |
| `invalid-input` | The input is not a JSON object, has a cycle, or fails the input schema (`issues` lists each failure with a JSONPath) |
| `input-too-large` | The input is over `limits.inputBytes` |
| `not-found` | A named thing does not exist (an unknown component or theme id) |
| `runtime-unavailable` | The door does not serve the operation's runtime class |
| `invalid-output` | The handler returned output outside its output schema (a bug in Texuli) |
| `timeout` | The handler ran past `limits.timeMs` |
| `operation-failed` | The handler threw an unexpected error |

### Schemas

The validator is owned code (`src/ops/schema.ts`, `validateJson`) for the
subset of JSON Schema 2020-12 the operations use: `type`, `enum`, `const`,
`properties`, `required`, `additionalProperties`, `items`, `minItems`,
`maxItems`, `minLength`, `maxLength` (code points), `pattern` (Unicode),
`minimum` and `maximum`, plus the annotations `title`, `description`,
`default`, `examples` and `$comment`. A schema that uses any other keyword is
refused when the registry is built (`schemaKeywordIssues`), so no constraint
is silently ignored. Every input schema is an object with
`additionalProperties: false`, so unknown arguments are refused by name.

## Removed 0.8 tool names

The seven MCP tool names of `0.8` (`deck`, `document`, `catalog`,
`component`, `validate`, `example`, `theme`) were deprecated aliases in
`0.9.0` and are removed in `0.10.0`. No door lists them. A call is refused with a message that
names the operation to call instead: `invoke()` returns `unknown-operation`
with `The tool "theme" was removed in 0.10.0; call theme.search or
theme.get instead.`, and the MCP `tools/call` answers the same text as a
`-32602` protocol error. The generated table under
[Operations](#operations) lists each name and its replacement
(`TEXULI_REMOVED_NAMES`, `registry.removed()`). Move host prompts and
allowlists: `deck` → `deck.run`; `document` → `document.run`, or
`document.export` with `format: "pdf"` or `"docx"` for the old `to-pdf` and
`to-docx` commands; `catalog` → `catalog.search`; `component` →
`component.get`; `validate` → `catalog.validate`; `example` →
`example.search`; `theme` → `theme.get` (with `id`) or `theme.search`.

The alias mechanism stays (`OperationAlias`, `registry.aliases()`, empty in
`0.10.0`): the next renamed operation keeps its old name for one minor
(ADR-017).

## Doors that use it today

- **MCP (in the repository source):** `createMcpHandler` ([mcp.md](mcp.md))
  generates `tools/list` from the registry: every operation of the runtime
  classes the door serves (`edge` and `node` for the local stdio server,
  `edge` and `site` for the remote endpoint, which passes each request's
  `env.ASSETS` as the site context),
  with `inputSchema`, `outputSchema`, `annotations` and cursor pagination,
  then any deprecated aliases (none in `0.10.0`). A call goes through `invoke()` and returns
  `structuredContent` plus a text mirror; a failure is an `isError` result
  whose JSON has `error`, `code` and, for schema failures, `issues`. An
  unknown tool name is a JSON-RPC `-32602` error. The same handler serves
  the resources, prompts and completions.
- **CLI:** `texuli <group> <verb>` (`src/cli/router.ts`) runs every
  `edge` and `node` operation (not the `site` ones): the input is one JSON object from stdin, `--json <object>` or
  `--file <path>`; the output is the operation's JSON on stdout (a refusal
  prints `{ ok: false, operation, error }` and exits 1), or `--out <path>`
  writes it through the local write policy (a new file inside the working
  directory; `--overwrite` replaces one). `texuli help`, `texuli <group>
  --help` and `texuli <group> <verb> --help` are written from the registry.
  The 0.8 commands stay: `texuli deck …` runs `deck.run`; `texuli document
  …` runs `document.run`, or `document.export` for `to-docx` and `to-pdf`;
  `texuli theme list` and `theme preview <id>` run `theme.search` and
  `theme.preview`; `texuli ds <command> <file>` runs the `ds.*` operations
  on files ([ds.md](ds.md#cli)), and `texuli ds check` the conformance
  check; `texuli init`, `theme apply`, `add`, `diff`, `update` and
  `mcp` route to their own commands, and every 0.8 bin (`texuli-init`,
  `texuli-deck` …) still works.
- **Generated surfaces:** the MCP server card, the "Tools" section of the
  site `llms.txt`, the tables on this page and the `/mcp-server/` page data
  come from `scripts/agent-surfaces.ts`; `pnpm check:surfaces` regenerates
  them into a temporary directory and fails on any difference.

## Tests

`packages/tools/tests/ops.test.ts` checks that every operation is declared
once in the schema subset, round-trips every example through its input and
output schemas, refuses bad input with each error code, refuses every
removed 0.8 name with its replacement, reads the version from
`package.json`, and that the CLI runs through the registry.
The same file checks `blueprint.validate` on golden and hostile fixtures,
envelope migration, the catalog hash, deep block checks, the frame root,
the node cap and the input cap.
`packages/tools/tests/blocks-ops.test.ts` checks that `block.list` and
`block.schema` serve every validated block type, that every served example
passes the family check and `blueprint.validate`, that every required field
is one the parser refuses a block without, and that `block-schema`
diagnostics name the expected shape.
`packages/tools/tests/router.test.ts` checks the router: every operation
example through `--json`, stdin and `--file`, the kept commands, refusals,
hostile input, `--out` under the write policy, and the `texuli help`
snapshot (`tests/__snapshots__/texuli-help.txt`).
`packages/tools/tests/mcp.test.ts` covers the MCP tool list and calls,
`packages/tools/tests/mcp-protocol.test.ts` is the MCP conformance suite, and
`packages/catalog/tests/manifests-all.test.ts` checks the static manifest
list builds the same catalog hash as file-system discovery.
`packages/tools/tests/site-ops.test.ts` checks the `site` operations against
a fake `env.ASSETS` (`tests/fixtures/site-assets.ts`): that only the remote
runtimes list them, every accepted path form, traversal and foreign-host
refusals (and that a refused path never reaches the fetcher), pagination,
the deterministic ranking and its tie-breaks, the 256 KiB read cap, the
once-per-binding manifest read and broken manifests.
